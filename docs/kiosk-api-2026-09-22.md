# Kiosk backend contract — 22 September 2026

These changes are implemented locally, not deployed. Apply the SQL migration before deploying services. Deploy the kiosk client changes below together with the backend: anonymous sockets and unauthenticated device mutations now fail closed.

## 1. Credentials and lifetime

The chosen option is **direct linked-device authentication**, rather than a refresh endpoint. Use the opaque `session_token` from `POST /api/vendors/{vendorId}/pcs/link` as `Authorization: Bearer <session_token>` for kiosk runtime calls. It does not expire with time: it is valid while the matching `console_link_sessions` row is `active`. Closing/unlinking the row immediately prevents subsequent requests and event delivery. Relinking issues a new token; an invalid/revoked link requires staff setup again. Protect this token in the OS credential store.

Vendor setup calls (PC list, link, staff unlink) require a valid vendor JWT belonging to that vendor. Runtime endpoints also accept authorized vendor/staff JWTs for dashboard operations. Kiosk tokens cannot manage other PCs or vendors or use PC management endpoints.

`/api/validatePin` returns `data.expires_in` in **seconds**. The checkout defaults to `JWT_EXP_HOURS=24`, clamped to 1–168 hours. The response now uses that same clamp. The actual production environment value has not been inspected. Existing `/api/refresh-token` only refreshes an unexpired vendor JWT; it is not the kiosk recovery mechanism.

JWT errors use 401 and `{"status":"error","code":"token_expired"}` or `token_invalid`. Missing credentials return `token_required`; invalid/closed device credentials return `invalid_session_token`. Scope mismatches return 403.

## 3. Server time and expiry

`GET /api/bookings/{bookingId}/remaining` on the dashboard service requires the device bearer token. Authorized dashboard JWT callers also supply `?console_id=...`.

```json
{
  "status": "success",
  "data": {
    "booking_id": 1025,
    "booking_ids": [1025],
    "console_id": 10,
    "vendor_id": 1,
    "game_id": 100,
    "user_id": 77,
    "user_name": "Player",
    "status": "active",
    "seconds_remaining": 600,
    "start_time": "2026-09-22T06:30:00+00:00",
    "end_time": "2026-09-22T07:30:00+00:00",
    "server_time": "2026-09-22T07:20:00+00:00"
  }
}
```

`data.status` is `active`, `expired`, or `cancelled`; inactive responses have zero remaining seconds. Windows come from server booking records, interpreting stored schedule dates/times as Asia/Kolkata and returning explicit UTC offsets. Overnight windows are supported; zero-length/incomplete schedules are rejected. Contiguous assigned bookings under the same access code form one paid window. Poll every 30–60 seconds, use server remaining seconds for the display, and lock on expiry/cancellation. Do not replace malformed timestamps with five free minutes.

The dashboard starts an expiry sweep immediately on process start and every 30 seconds thereafter (`KIOSK_EXPIRY_ENABLED=true`, default). It completes elapsed booking rows and frees consoles only when no unexpired current booking still occupies them. Cancellation is preserved. PostgreSQL advisory locks serialize expiry, kiosk redemption, and device-status changes across workers. It works without the kiosk calling release and catches up after a server restart. Keep the service running; no process can update records while the service itself is down. Remaining-time reads also reconcile that vendor first.

Server accounting cannot physically stop a tampered/offline Windows application. The client must enforce its lock screen and decide its offline grace policy; backend deadlines remain authoritative regardless.

## 4. Socket contract

Use the returned `ws_url` as the Socket.IO host, with path `/socket.io`. It previously contained a placeholder host; it now comes from `KIOSK_WS_URL`, or the request host when unset. No per-vendor routing is configured in the source. Set `KIOSK_WS_URL` to the public dashboard Socket.IO origin behind a proxy.

Handshake:

```js
io(ws_url, {
  path: '/socket.io',
  transports: ['websocket'],
  auth: { session_token, console_id }
});
```

The server rejects unauthenticated connections and mismatched console claims. It derives a room from the active link row, not a client-supplied ID. `kiosk_join` is optional; if sent, use `{console_id}`. The legacy `{kiosk_id: console_id}` alias is checked against the authenticated console. `kiosk_id` in `/link` remains the installation identifier string; it is not a console number.

`unlock_request` is delivered once to the active link room with the fields shown in `data` above at the event's top level, plus `type: "unlock_request"`. `session_expired` carries `console_id`; polling is authoritative if an event is missed. Revoked connections receive no further kiosk events. Continuation socket requests are checked against the authenticated device and running booking. Client-triggered demo broadcasts were removed. `/internal/ws/unlock` now requires an authorized bearer and derives its deadline from server records.

Dashboard browser sockets must send `auth: {token: vendorJwt}`. The bundled dashboard's socket context was updated accordingly, including reconnecting after credentials become available.

## 5. Redemption and unlink

`POST /api/bookingQueue` remains on the onboard service and proxies to dashboard `/api/kiosk/start-session`, forwarding Authorization. Send the device token plus `{console_id, access_code}`. A booking ID alone is insufficient for a kiosk. All supplied booking/vendor/game IDs must agree with database records. Kiosk credentials cannot select additional devices; staff assign squad consoles through the dashboard.

Codes are not originally issued to a PC: booking purchase can precede console selection. Redemption now binds the code to the authenticated console and original booking atomically. An already assigned booking must match that console. Another PC cannot redeem the same code, and a completed redemption cannot start another session. An in-flight session can be fetched again by the same console to recover a lost response. Failed starts roll back both code consumption and booking changes.

Limits are persisted in PostgreSQL across workers: 10 redemption attempts per console/minute, 60 per source IP/minute. Onboard also limits the original client IP before proxying; dashboard independently limits direct calls (the onboard service shares its proxy IP bucket). Limits return 429 with `Retry-After: 60`. Ensure trusted-edge proxy settings match the deployment; do not expose a proxy-trusting app port directly.

`POST /api/kiosk/unlink` accepts the token in the JSON body with optional `console_id`, `vendor_id`, and installation `kiosk_id`. The token is required. Any supplied identity field must match. IDs alone never authorize unlinking.

## 6. Response and retry contract

`bookingQueue` success always has one envelope: `{"status":"success","data":{...}}`, including `data.user_name`, `data.booking_id`, and explicit UTC timestamps. Errors use non-2xx status codes. Application-level unhandled failures return JSON; an external gateway can still generate its own HTML error page, so retain the client's non-JSON fallback.

Device start/release accept `Idempotency-Key` (also `X-Idempotency-Key`), at most 128 characters. Reuse the same random key and exact path/body for retries. Successful JSON responses and the state mutation commit atomically. Same key/different request returns 409 `idempotency_conflict`; failed mutations roll back and can be retried. Records currently remain until operational cleanup; retain them for the full supported replay horizon.

For kiosk release, additionally send `{"booking_id":1025}`. This prevents a late retry from releasing the next customer's booking. Kiosk `updateDeviceStatus` acknowledges the already redeemed active booking; access-code redemption starts the session. Vendor dashboard operations retain their existing start/release behavior.
